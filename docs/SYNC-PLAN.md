# План: общие данные для семьи (синхронизация через облако)

Решение пользователя (2026-10-31): приложением пользуются двое — записи вносят оба,
поэтому данные должны быть общими. Дополнение к ТЗ — раздел 4.15.

## Как это будет работать для вас

1. Один раз регистрируетесь в Supabase (бесплатно), создаёте проект, вставляете туда
   готовый скрипт `docs/supabase-setup.sql` — он создаёт таблицу для записей и правила доступа.
2. В приложении: «Ещё → Настройки → Общие данные» — вставляете адрес проекта и публичный
   ключ (их показывает Supabase), нажимаете «Создать семейный код». Приложение выгружает все
   ваши записи в облако.
3. Нажимаете «Скопировать код подключения» и отправляете мужу (одна строка текста).
4. Муж открывает приложение на своём телефоне, «Ещё → Настройки → Общие данные → Подключиться
   по коду», вставляет строку. Его телефон получает все записи.
5. Дальше всё само: записал один — через несколько секунд видит другой. Без интернета
   приложение работает как раньше и дошлёт записи, когда связь появится.

Что хранится в облаке: операции, категории и статьи, бюджет, курсы, расписания, платежи,
долги, желаемые покупки, продукты, банки. **Фото чеков в облако не попадают** (они большие
и видны только на том телефоне, где сняты) — это ограничение первой версии.

Кто видит данные: только тот, у кого есть семейный код (длинная случайная строка). Без кода
облако ничего не отдаёт. Код можно сменить в настройках — старый перестанет работать.

## Как это устроено (для исполнителя)

- **Облако:** Supabase, одна таблица `records(family, store, id, data jsonb, updated_at, deleted)`.
  Доступ через публичный ключ + заголовок `x-family` с семейным кодом; правила RLS
  пропускают только строки своей семьи. Триггер в базе не даёт старой записи затереть новую.
- **Журнал изменений:** в IndexedDB новое хранилище `changes` (store, id, updatedAt, deleted).
  Любая запись или удаление через `put` / `remove` в `src/db.js` в синхронизируемом
  хранилище попадает в журнал (миграция 14; у всех записей появляется `updatedAt`).
- **Обмен (`src/sync.js`):** отправка — журнал пачками upsert; получение — строки с
  `updated_at` позже сохранённой отметки; применяется та версия записи, у которой
  `updatedAt` новее (последняя правка побеждает); удаление — пометка `deleted`.
  Запуск: при открытии, через 2 с после любой записи, при появлении сети, раз в 5 минут.
- **Настройки** (`settings`): `sync` = { url, key, family, cursor, lastAt, lastError };
  в резервную копию не входят.
- **Подключение к семье при уже имеющихся записях:** предупреждение и выбор — «Заменить мои
  записи общими» (рекомендуется для второго телефона) или «Объединить» (записи сольются;
  категории с одинаковыми названиями объединяются по имени).
- **Резервная копия:** восстановление при включённых общих данных предупреждает и после
  восстановления отправляет все записи в облако (без удалений).
- **Статус** в настройках: «Общие данные: обновлено 12:03 · ожидают отправки 3 · нет связи».

## Этапы

1. **Подключение.** Миграция 14 (`updatedAt` везде, хранилище `changes`, журналирование в
   `put`/`remove`), экран «Общие данные» (адрес, ключ, создать код / подключиться по коду /
   скопировать код подключения / отключить), скрипт `supabase-setup.sql`, проверка связи.
   Тесты: журнал изменений, разбор кода подключения.
2. **Обмен.** `src/sync.js`: отправка и получение, последняя правка побеждает, удаления,
   запуск по событиям, статус и ошибки. Тесты: слияние записей, очередь, повторы при ошибке.
3. **Второй телефон и крайние случаи.** Подключение при имеющихся записях (заменить /
   объединить), восстановление копии при общих данных, проверка на двух «телефонах»
   (две базы в браузере), памятка.

Что от пользователя: регистрация в Supabase и вставка скрипта (этап 1); проверка на двух
телефонах (этап 3). Ключи вставляются только в приложение; в чат их присылать не нужно.
